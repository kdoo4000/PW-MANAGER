# 매치엔진 시스템 기획서 작성 가이드

작성 기준일: 2026-10-14

## 1. 좋은 시스템 기획서의 기준

좋은 시스템 기획서는 다른 사람이 문서만 읽고 같은 규칙을 구현하고, 같은 상황에서 같은 판정을 내리고, 결과가 올바른지 검증할 수 있는 문서다. 이 정의는 아래 자료를 PWMANAGER에 적용한 정리이며, 업계의 단일 표준 양식은 아니다.

- **목적:** 규칙이 어떤 플레이 경험과 선택을 만드는지 설명한다.
- **명확성:** 입력, 조건, 처리 순서, 출력, 예외를 구체적으로 적는다. ‘적절히’, ‘일정 확률’, ‘상황에 따라’로 규칙을 끝내지 않는다.
- **일관성:** 같은 용어와 수치를 모든 절에서 사용한다. 계획된 결과와 실제 결과를 구분한다.
- **검증 가능성:** 정상 사례, 경계값, 실패 사례에 기대 결과를 붙인다.
- **탐색성:** 흐름은 도식, 규칙은 조건표, 수치는 데이터 표로 정리하고 관련 절을 연결한다.
- **유지 가능성:** 기준 버전, 수정일, 변경 이유, 미결정 사항을 관리한다.

Game Developer의 현대 GDD 가이드는 프로젝트에 맞는 형식, 명확한 전달, 검색하기 쉬운 구성, 플레이 경험 목표를 강조한다. 전체 게임 기획서의 항목을 매치엔진 문서에 모두 옮기기보다 해당 시스템의 의사결정에 필요한 내용을 선택한다.

출처: [How To: Write a Game Design Document](https://www.gamedeveloper.com/design/how-to-write-a-game-design-document)

기존 설계 문서 가이드는 규격뿐 아니라 의도와 경험을 전달하고, 가독성과 우선순위를 확보할 것을 강조한다. 따라서 현재 코드에서 확인한 동작과 앞으로 원하는 동작을 구분해야 한다.

출처: [Creating A Great Design Document](https://www.gamedeveloper.com/design/creating-a-great-design-document)

Unity의 GDD 템플릿은 전체 게임 문서의 구성 참고용이다. 이 문서는 그보다 좁은 매치엔진 시스템 명세를 다룬다.

출처: [Unity GDD Template](https://connect-prd-cdn.unity.com/20201215/83f3733d-3146-42de-8a69-f461d6662eb1/Game-Design-Document-Template.pdf)

## 2. 현재 엔진에서 확인한 문서화 대상

기존 graphify 그래프의 MatchPlanState, MatchEvaluator, MatchFinishRules 및 연결을 먼저 조회하고 현재 소스를 확인했다. graphify CLI는 실행 경로 오류로 동작하지 않아 기존 graph.json을 직접 조회했다. 그래프는 현재 소스보다 오래된 항목을 포함하므로 아래 세부 규칙은 소스 확인을 기준으로 한다.

이 문서는 작성 준비용 목차다. 모든 분기와 공식을 전수 검증한 완성 명세가 아니며 Unity 실행 검증은 수행하지 않았다. 테스트 항목은 기존 테스트 소스에서 확인한 검증 주제이며, 통과 결과를 의미하지 않는다.

- 경기 계획: 대전 진영과 구성원, 승리 진영, 피니시 수행자와 패배 대상, 오프닝, 스팟, 다전·아이언맨·탈락·토네이도 설정, 스토리라인·챔피언십 연결.
- 경기 진행: Opening, Neutral, Control, Comeback, BackAndForth, Climax, Finish의 7개 상태와 행동 선택.
- 선수 상태: 능력치, 스타일, 피로, 주도권, 행동 준비도, 자세, 위치, 부위별 손상, 실제 부상, 시그니처·피니셔.
- 기술·스팟: 기술 사용 조건과 수행·접수, 계획된 스팟의 평가, 모션 데이터.
- 종료: 예약된 승패·종료 방식, 경기 규칙별 허용 판정, 부상 중단과 대체 마무리.
- 결과: 실제 승패·시간, 기술적 평가, 팬 반응, 후속 변화, 부상·컨디션 변화, 이벤트·서술·재현용 시드.

현재 Simulate에서 기록하는 EngineVersion은 4다. 이를 문서 기준 정보로 기록하되, 모든 기능이 버전 번호만으로 고정된다고 가정하지 않는다.

## 3. 권장 목차와 각 장에 들어갈 내용

### 01. 시스템 목적과 범위

매치엔진이 제공하려는 경험, 경영 게임에서의 역할, 플레이어가 통제하는 범위, 엔진이 결정하는 범위를 적는다. 경기 편성·스토리·팬 평가·경기 재생과의 경계를 정의한다.

의도 후보: ‘플레이어의 경기 계획을 선수 역량과 경기 규칙에 맞춰 수행하고, 과정의 완성도와 사고를 결과로 돌려준다.’ 이는 코드에서 추출한 확정된 기획 의도가 아니라 검토할 문장이다.

### 02. 용어와 핵심 개념

매치, 진영, 태그팀, 합법 참가자, 주도권, 피로, 부위 손상, 실제 부상, 각본상 부상, 셀링, 스팟, 시그니처, 피니셔, 예약 피니시를 정의한다. 특히 부위 손상·실제 부상·각본상 부상을 동일한 개념으로 쓰지 않는다.

### 03. 플레이어 입력과 경기 계획

어떤 화면에서 무엇을 설정하며 각 설정이 어디에 영향을 주는지 연결한다. 참가자·팀 구성, 경기 유형·기믹, 목표 시간, 승리 진영, 피니시 수행자·대상, 오프닝, 스팟, 스토리 부상을 다룬다.

각 입력에는 필수 여부, 기본값, 허용 범위, 다른 입력과의 제약, 유효하지 않을 때의 처리 방식을 붙인다. 모델에 필드가 있다는 사실만으로 플레이어가 화면에서 직접 설정할 수 있다고 단정하지 않는다.

### 04. 전체 처리 흐름

계획 입력 → 검증 → 참가자·규칙 구성 → 초기 상태 생성 → 경기 진행 반복 → 종료 또는 중단 → 평가 → 후속 변화 적용 → 결과 표시의 흐름을 정리한다. 이 순서는 문서화용 상위 흐름이며 실제 호출 순서는 실행 서비스까지 추적해 확정한다.

반복 처리 안에서는 행동 후보 생성, 수행자·대상 선택, 사용 가능 판정, 실행·접수·반격 판정, 상태 변화, 사고·스팟·종료 검사, 시간·로그 기록의 실제 순서를 명시한다. 같은 프레임이나 이벤트에서 조건이 겹칠 때 어느 판정이 먼저인지가 중요하다.

### 05. 경기 유형과 규칙 조합

개인전·태그전, 참가자·진영 수, 다전, 아이언맨, 탈락, 토네이도, 기믹별 목표와 허용 종료 방식을 정리한다. 지원 조합과 금지 조합을 별도로 표시한다.

조건표 예시: 기본 규칙에서 실격·카운트아웃은 개인전 참가자가 3명 미만이거나 팀전 진영이 3개 미만일 때 허용한다. 기믹의 명시적 허용·금지 설정은 기본값보다 우선한다. 탈출·물체 획득·테이블 파괴는 기믹의 허용 특수 종료 목록에 포함되어야 한다.

근거: `Assets/Game/Domain/Services/MatchFinishRules.cs`

### 06. 선수 능력치와 경기 중 상태

능력치별 역할, 입력 범위, 초기값, 증가·감소 조건, 최소·최대값, 경기 후 유지 여부를 적는다. 수행, 기술·타격·파워·공중기, 경기 운영·즉흥 대처, 셀링, 체력, 스타일·케미스트리가 어떤 판정에 쓰이는지 추적한다.

경기 중 피로·주도권·행동 준비도·부위 손상·스턴·자세·위치·합법 참가 여부를 구분한다. ‘체력이 낮으면 불리하다’ 대신 무엇의 확률이나 점수가 어떻게 변하는지 적는다.

### 07. 경기 단계와 전환

7개 상태별 목적, 진입·이탈 조건, 전환 후보 점수, 행동 및 수행자 선택 보정을 적는다. 이름을 시간순으로 나열하는 것만으로는 부족하다. 이전 단계로 돌아갈 수 있는지와 여러 전환 후보가 동시에 유효할 때 선택 방식도 명시한다.

근거: `MatchStateMachine.cs`, `MatchOpening.cs`

### 08. 행동·기술 선택과 판정

행동 종류, 후보 조건, 스타일·능력치 가중치, 대상 선정, 자세·위치·그립 제약, 준비 동작, 수행 성공·부분 성공·실패·접수 실패·반격을 다룬다. 결과마다 손상, 피로, 자세, 위치, 다음 행동에 주는 영향을 연결한다.

기술 데이터에는 ID, 이름, 행동·상황·종류, 타격 부위, 허용 스타일, 일반·시그니처·피니셔 가능 여부, 능력치 가중치, 수행·셀링 난도, 요구 능력치, 모션, 종료 자세, 이동 거리가 있다. 각 필드의 단위·기본값·유효성 규칙까지 표에 붙인다.

근거: `MatchTechniques.cs`, `MatchMoveService.cs`, `MatchPhysics.cs`, `MatchMoves.csv`

### 09. 계획된 스팟

스팟 종류, 참가자, 실행 시점, 필요 조건, 성공·실패 확률, 반복 사용 감점, 점수·상태·종료에 미치는 영향을 정리한다. 예정 시점에 실행 불가능할 때 연기·취소·대체 중 어떤 처리를 하는지도 확인한다.

근거: `MatchSpotState.cs`, `MatchSpotEvaluator.cs`, `MatchSpotCatalog.cs`, `NormalMatchSpotCatalog.cs`

### 10. 승패·종료·예약 피니시

예약 승자와 실제 승자, 피니시 수행자와 패배 대상, 종료 방식별 조건을 분리한다. 핀·서브미션·롤업·실격·카운트아웃·무승부·특수 목표, 로프 브레이크·태그 방해·심판 상태, 다전·탈락의 처리와 우선순위를 정리한다.

현재 시간 규칙 예시: 아이언맨이 아니며 Booking이 있고 예약 종료가 Draw가 아닐 때 허용 오차는 목표 시간의 정수 나눗셈 `TargetDurationSeconds / 20`이다. 목표 720초라면 36초이며 기본 종료 구간은 684~756초다. 그 외 조건에서 이 오차는 0초다. 구조 대처 기한이 있으면 최종 종료 한계는 `max(목표 시간 + 오차, RescueDeadline)`이므로 항상 ±5% 안에 끝난다고 적으면 틀린다.

근거: `MatchEngineState.DurationToleranceSeconds`, `EarliestFinishSeconds`, `LatestFinishSeconds`

### 11. 사고·부상·중단·대체 진행

사고 발생 조건과 확률, 피해 대상·부위·심각도 결정, 기술 사용·접수 제한, 안전한 대체 피니시, 의료 중단, 정상 진행 실패를 다룬다. 경기 후 회복 일수와 결장, 중복 적용 방지까지 연결한다.

현재 의료 중단 처리 `RecordStop`은 승자 없음, 실제 종료 Draw를 기록한다. 계획된 승자 유지와 안전한 마무리가 충돌하는 상황은 별도의 우선순위 규칙으로 설명해야 한다. 예외를 일반적인 경기 종료에 섞지 않는다.

근거: `MatchHealth.cs`, `MatchHealthTests.cs`

### 12. 경기 평가와 후속 영향

수행·구조·판단·셀링의 관찰값, 경기 시간·스팟·변동 요소, 최종 경기 품질, 비평·별점, 팬 반응, 스토리 평가를 구분한다. 어떤 점수가 어떤 점수의 입력인지와 범위·가중치·반올림·상하한을 적는다.

현재 ObserveQuality는 이벤트를 근거로 수행·구조·판단·셀링을 계산한다. 따라서 ‘선수 능력치가 높으면 평점이 높다’만으로는 엔진 평가를 설명할 수 없다. 관찰 근거가 없는 경우의 기본값도 포함한다. 저장 모델의 필드가 실제로 갱신되는지는 호출부 확인이 필요하다.

근거: `MatchEvaluator.cs`, `MatchResultState.cs`, `ShowExecutionService.cs`

### 13. 결과 화면과 경기 재생

결과 화면에 필요한 승패, 실제 시간, 주요 장면, 평가 근거, 부상·컨디션 변화, 실패 사유를 정의한다. 재생은 이벤트의 전후 상태, 위치·자세·모션, 타임라인, 해설과 연결한다. 계산 결과와 표시·연출의 책임을 구분한다.

선수 이름은 선수 ID로 프로필에 연결한다. 기존 프로젝트 원칙에 따라 단독 이름은 WrestlerProfileController.CreateLink, 문장 속 이름은 WrestlerNameText를 사용한다.

### 14. 데이터·밸런스·재현

기술, 모션, 스팟, 경기 유형·기믹, 능력치 보정, 확률·계수의 데이터 사전을 만든다. 필드는 이름·타입·단위·범위·기본값·용도·원본 위치를 기록한다. 조정 가능한 값과 코드에 고정된 규칙을 구분한다.

시드와 엔진 버전, 동일 입력의 범위를 정의하고 재현 사례를 보관한다. 밸런스 목표에는 실제 시간 편차, 피니시 일치율, 실패·부상 발생률, 평점 분포 등 측정 대상을 정한다. 목표 숫자는 별도 기획 결정이며 현재 구현값과 혼동하지 않는다.

### 15. 검증 사례와 미결정 사항

각 사례를 ‘입력/상태 → 처리 → 기대 결과’로 작성한다. 최소한 정상 개인전, 태그 합법 참가자, 금지 종료, 예약 피니시 시간 경계, 아이언맨 정확한 시간, 경미·중간·중대 부상, 안전한 대체 불가, 부상 셀링 연속성, 원본을 변경하지 않는 미리보기를 다룬다.

기존 테스트를 명세 사례의 출발점으로 활용하되 코드 동작이 곧 바람직한 기획이라는 결론은 내리지 않는다. 원하는 규칙과 구현이 다르면 ‘변경 제안’으로 적는다.

## 4. 개별 규칙의 작성 양식

```text
규칙 ID / 이름:
상태: 현재 구현 확인 / 변경 제안 / 미결정
목적: 어떤 선택이나 경험을 만드는가
적용 범위:
입력 및 사전 조건:
처리 순서와 우선순위:
공식: 변수 정의, 단위, 범위, 상하한, 정수 처리 포함
출력 및 상태 변화:
예외와 실패 처리:
정상 예시:
경계·실패 예시:
데이터·코드 근거:
검증 사례:
```

한 규칙에서 공식을 설명하고 다른 장에는 링크한다. 같은 공식을 여러 장에 복사하면 변경 시 불일치가 생긴다. 코드 위치는 부록의 근거로 유지하고, 본문은 기획 용어로 설명한다.

## 5. 작성 순서

1. 목적·범위와 플레이어 통제 범위를 먼저 확정한다.
2. 입력 → 진행 → 종료 → 평가의 전체 흐름을 한 장에 그린다.
3. 예약 피니시, 시간, 부상 중단의 우선순위를 작성한다.
4. 단계·행동·기술·스팟·능력치와 공식을 채운다.
5. 데이터 사전, 화면 연결, 검증 사례를 붙인다.
6. 모든 항목을 현재 구현·변경 제안·미결정으로 표시하고 기준 버전과 수정 이력을 기록한다.

첫 초안의 핵심은 ‘예약된 경기 계획이 실제 경기 과정과 결과로 어떻게 변환되는가’를 끝까지 설명하는 것이다.
