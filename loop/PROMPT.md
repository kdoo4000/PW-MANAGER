# ① 합격 기준 (한 문장)
이걸 다른 사람이 봤을 때, 특히 스포츠 시뮬레이션을 즐겨하거나 프로레슬링을 좋아하는 사람들이 봤을 때에도 퀄리티가 떨어지지 않으며 UI로 인해 불편을 겪지 않을까?

# ② 먼저 읽을 문서

1. `docs/feedback/INBOX.md`
   - 어디까지 읽을지: 문서 전체. 현재 지시와 사용자 추가 피드백을 가장 먼저 확인한다.
2. `docs/DESIGN.md`
   - 어디까지 읽을지: 문서 전체. 제품 방향, 확정 규칙, 범위와 품질 원칙을 확인한다.
3. `docs/STATUS.md`
   - 어디까지 읽을지: 문서 전체. 현재 구현 상태, 연결 공백, 다음 한 작업과 완료 조건을 확인한다.

# ③ 규칙과 근거

- 규칙: 한 바퀴에는 `STATUS.md`의 "다음 한 작업" 하나만 완료한다.
  - 왜: 작업 범위를 작게 유지해야 중단되어도 검증과 복구가 쉽고, 루프가 미완성 변경을 누적하지 않는다.
- 규칙: 게임 시작 → 시간 진행 → 쇼 개최 → 결과 반영의 플레이 가능한 핵심 루프를 우선한다.
  - 왜: 개별 시스템이 많아도 실제 플레이 흐름으로 연결되지 않으면 프로토타입의 가치를 검증할 수 없다.
- 규칙: 지금 필요한 MVP와 후순위 확장을 분리하고, 완료 조건 밖으로 확장하지 않는다.
  - 왜: 장기 스토리, 세분화된 팬 반응과 범용 구조를 먼저 만들면 핵심 루프 완성이 늦어진다.
- 규칙: 선수·계약·자금·일정은 각각 하나의 원본 데이터만 사용하고 파생값을 중복 저장하지 않는다.
  - 왜: 같은 사실을 여러 곳에 저장하면 결과 반영과 저장·불러오기에서 서로 다른 값이 생긴다.
- 규칙: 입력과 무작위 시드가 같으면 같은 결과가 나오도록 구현한다.
  - 왜: 시뮬레이션 결과를 재현할 수 있어야 버그, 밸런스와 회귀를 정확히 검증할 수 있다.
- 규칙: 점수와 상태 변화는 화면 또는 로그에서 원인을 추적할 수 있어야 한다.
  - 왜: 스포츠 경영 시뮬레이션은 결과 자체뿐 아니라 왜 그런 결과가 나왔는지 이해하는 과정이 핵심 경험이다.
- 규칙: 정상 흐름과 함께 경계값, 실패 상황, 중복 실행, 저장·불러오기를 검사한다.
  - 왜: 장기 세이브를 다루는 경영 게임에서는 조용한 데이터 손상과 결과 중복이 치명적이다.
- 규칙: 기획과 구현이 다르면 기획을 임의로 바꾸지 말고 차이를 `STATUS.md`에 기록한다.
  - 왜: 구현 편의에 맞춰 원본 기획을 바꾸면 제품 의도와 코드의 차이를 검토할 수 없게 된다.
- 규칙: 화면 작업은 스포츠 시뮬레이션과 프로레슬링 팬의 관점에서 정보 우선순위, 용어, 가독성을 검토한다.
  - 왜: 기능이 동작해도 핵심 정보를 찾기 어렵거나 장르 용어가 어색하면 플레이 품질이 떨어진다.
- 규칙: 사용 여부가 불확실한 범용 계층, 설정, 확장 지점을 미리 만들지 않는다.
  - 왜: 실제 요구가 생기기 전의 추상화는 코드와 테스트 비용을 늘리고 책임 경계를 흐린다.

# ④ 한 바퀴 도는 순서

읽기 → 하나만 만들기 → 실행해서 눈으로 확인 → 커밋 → `STATUS.md` 갱신

# ⑤ 커밋 순서 규칙

검사를 통과하면, 화면을 보기 "전에" 일단 커밋한다.

한 바퀴는 도중에 멈춘다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다.

# ⑥ 검사와 QA

- 화면이 있는 것을 만들면, 실행해서 스크린샷을 찍고 그 이미지를 직접 읽어라. 코드가 도는 것과 화면이 괜찮은 건 다른 문제다.
- 같은 지적이 두 번 나오면 규칙으로 올리고, 기계가 잴 수 있는 규칙이면 검사로 만들어 둬라. 한 번 겪은 고장을 두 번 겪지 않는다.
