# 게임 데이터 설계 우선순위

화면 구현보다 게임 데이터, 계산식, 결과 적용 규칙을 먼저 확정한다.

## 목표

- 같은 저장 데이터와 시드에서 같은 결과가 나온다.
- 화면은 계산하지 않고 확정된 도메인 결과만 표시한다.
- 저장할 원본값과 실행 중 계산할 파생값을 구분한다.
- 계산식 변경은 좁은 EditMode 테스트로 검증한다.

## 현재 구현된 기반

- 저장 루트: `GameSave`
- 선수 상태: `WrestlerState`와 하위 상태
- 경기 능력치 요약: `WrestlerOverallCalculator`
- 경기 평가: `MatchEvaluator`
- 프로모 평가: `PromoEvaluator`
- 티켓 가격: `TicketPricingRules`
- 초기 계약 제안: `InitialContractOfferRules`
- 시즌 일정: `SeasonScheduleGenerator`
- 날짜 진행, 급여, 계약 만료: `TimeFlowService`
- 쇼 결과 반영: `ShowResultApplicationService`
- 저장 검증: `GameSaveValidator`

## 확정 순서

### 1. 공통 수치 규칙

Notion의 선수 능력치, 선수 성장, 경기 결과 및 평가, 계약 및 재정 문서를 기준으로 다음 항목은 확정된 것으로 본다.

| 대상 | 형식·범위 | 처리 규칙 |
|---|---|---|
| 선수 경기·프로모 능력치 | `float`, `1.0~20.0` | 소수점 값을 유지하고 화면에는 등급 표시 |
| 경기·프로모 잠재력 | `float`, `1.0~20.0` | 경기 총합은 `잠재력 × 10`, 프로모 총합은 `잠재력 × 7` 이하 |
| 능력 등급 | `SS~E` | 반올림 전 실제 `float` 값으로 경계 판정 |
| 종합 능력 | 파생 `float`, `1.0~20.0` | 현재 스타일·역할에 따른 가중 평균으로 계산 |
| 컨디션·만족도·위상·모멘텀 | `float`, `0~100` | 기본 능력치와 분리된 현재 상태 |
| 팬 반응 | `float`, `-100~100` | 음수와 양수 반응 허용 |
| 경기·프로모·쇼 평가 | 비공개 `float` | 내부 계산과 기록 정렬에만 사용하고 UI에는 숫자를 공개하지 않음 |
| 평론가 별점 | 파생 `float` | 경기와 쇼의 기술·구성·스토리 완성도를 평가해 UI에 표시 |
| 팬 별점 | 후속 범위 | 팬 시스템 도입 전에는 계산·표시하지 않음 |
| 확률 | 퍼센트 `float`, `0~100` | 필드와 변수 이름에 `Percent` 사용 |
| 금액 | `long` | 수입은 양수, 지출은 음수, 0원 거래 금지 |
| 현재 자금 | 파생 `long` | `초기 자금 + 유효 거래 합계` |
| 티켓 설정 가격 | 기준가의 `60~160%` | 수요 배율은 기울기 `0.75`의 선형식 사용 |
| 가중치 합 | `float` | 경기 종합 10, 프로모 종합 7, 정적 콘텐츠 가중치 합 오차 `0.001` 허용 |

등급 경계는 `SS 19`, `S+ 18`, `S 17`, `A+ 16`, `A 15`, `B+ 14`, `B 13`, `C 10`, `D 7`, 그 미만 `E`다. 능력치와 모든 평가 계산은 내부 소수점을 유지한다. 능력치 숫자와 평가 점수는 UI에 공개하지 않고 각각 능력 등급과 별점으로만 표시한다.

#### 결과 표시 원칙

- 경기와 쇼 결과에는 `평론가 별점`을 표시한다.
- 프로모는 평론가 별점을 만들지 않는다. 내부 성공도는 변화량 계산에만 사용하고 UI에는 결과 요약과 주요 성공·실패 원인만 표시한다.
- 평론가 별점은 기술적·구성적 완성도와 제한적인 스토리 보정을 나타낸다.
- 팬 별점과 팬층별 반응·유입·이탈은 팬 시스템과 함께 후속 도입한다.
- 내부 점수, 세부 보정값, 난수 시드는 UI에 공개하지 않는다.
- 별점과 함께 각 평가의 주요 가점·감점 근거만 표시한다.

평론가 경기 평가는 Notion의 기존 기준을 따른다.

`TechnicalScore = FinalMatchQuality × 5`

`StoryModifier = (MatchStoryScore - 50) ÷ 10`

`FinalReviewScore = Clamp(TechnicalScore + StoryModifier, 0, 105)`

`FinalReviewScore`는 공개하지 않고 기존 비균등 구간표로 `0.25~7.00` 평론가 별점으로 변환한다. 같은 별점 안의 기록 순위는 소수점까지 유지한 내부 점수로 정렬한다.

쇼 평론가 평가는 기존 기준을 따른다.

`ShowReview = 경기 평균 × 0.55 + 상위 3개 경기 평균 × 0.20 + 쇼 흐름 × 0.15 + 스토리 완성도 × 0.10`

현재 코드도 능력치·잠재력·상태·팬 반응·계약 금액·0원 거래를 `GameSaveValidator`에서 검증한다. 범위를 벗어난 저장 데이터는 자동 보정하지 않고 검증 오류로 거부한다.

#### 구현 반영 완료

- 선수 종합 능력은 가중 평균을 사용한다.
- 결과 UI는 쇼·경기의 내부 점수 대신 평론가 별점을 표시한다. 프로모에는 평론가 별점을 표시하지 않는다.
- 확률은 `Percent` 접미사의 `0~100`으로 통일한다. `Ratio`, 배율, 관중 변동 basis point는 확률이 아니므로 기존 단위를 유지한다.
- 경기·기믹의 `Multiplier` 규칙값은 유한한 양수만 허용한다.
- 랜덤 생성값과 최종 파생 점수는 정의된 범위로 제한하고, 저장 데이터·정적 규칙·서비스 입력의 범위 초과는 오류로 거부한다.
- 저장 데이터와 현재 평가 경로의 `float` 입력에서 `NaN`과 `Infinity`를 거부한다.
- 금액의 일반 반올림은 `MidpointRounding.AwayFromZero`를 사용한다. 계약 제안처럼 명시적으로 올림하는 규칙은 별도 이름으로 유지한다.

#### 남은 후속 작업

- 단순 산술 평균으로 적힌 Notion 성장 문서를 가중 평균 기준으로 수정한다.
- 팬 시스템 도입 시 팬 별점 구간표, 최대 별점, 팬층별 반응 종합 공식을 확정하고 구현한다.
- 평론가 평가에 필요한 스토리 점수와 쇼 흐름 점수 생성기를 구현한다. 구현 전까지 두 입력은 중립값 `50`을 사용한다.

### 2. 원본값과 파생값

저장할 값:

- 선수 능력치, 컨디션, 성장, 모멘텀, 팬 반응
- 계약, 일정, 편성, 거래 내역
- 실행 결과와 결과 생성에 사용한 시드

계산할 값:

- 선수 Match/Promo Overall
- 현재 보유 현금
- 경기 및 프로모 예상 점수
- 표시 등급과 합계

파생값은 저장하지 않는 것을 기본으로 한다. 결과 재현이나 이력 보존에 필요한 값만 결과 상태에 저장한다.

### 3. 경기 평가

- 개인 기본 수행력
- 스타일, 경기 유형, 기믹 적합도
- 팀 조합과 공식 태그팀 케미
- 경기 구조와 스팟
- 예정 시간, 실제 시간, 체력 소모
- 실수, 부상, 명장면 발생 확률
- 승패와 피니시가 경기 품질 및 후속 변화에 주는 영향
- 최종 점수 계산 순서와 각 항목의 가중치

같은 입력과 `ResultSeed`에서는 참가자 순서가 달라도 동일한 결과가 나와야 한다.

### 4. 프로모 평가

- 발언자와 대상의 Promo Overall
- 성향, 역할, 관계, 스토리 적합도
- 프로모 유형과 목표
- 길이 및 반복 패널티
- 팬 반응, 관계, 스토리 변화량
- 최종 점수 계산 순서와 범위

### 5. 쇼 평가와 재정

- 경기와 프로모 점수의 쇼 전체 반영 비율
- 오프닝, 중간, 메인 이벤트 위치 가중치
- 관중 수요와 실제 관중 수
- 티켓 가격이 수요와 매출에 미치는 영향
- 방송, 스폰서, 상품 매출
- 대관, 인건비, 마케팅, 의료비
- 순이익과 명성 변화

`TransactionRecord`를 재정 원장으로 유지하고 현재 현금은 거래 합계로 계산한다.

### 6. 장기 변화

- 경기 후 컨디션과 부상
- 경험치와 능력치 성장 또는 하락
- 모멘텀과 팬 반응
- 관계와 태그팀 케미
- 계약 가치, 급여 요구액, 해고 비용
- 단기 변화와 영구 변화의 구분

### 7. 결과 적용 순서

1. 입력과 편성을 검증한다.
2. 저장된 시드로 경기와 프로모 결과를 만든다.
3. 쇼 평가와 재정 정산을 만든다.
4. 선수, 팬, 스토리, 계약, 재정 상태에 결과를 반영한다.
5. `ProcessedIds`로 중복 반영을 막는다.
6. 전체 저장 상태를 검증한 뒤 저장한다.

## 필요한 자료형 원칙

- ID 참조는 기존 `string` ID 방식을 유지한다.
- 날짜는 `GameDate`를 사용한다.
- 금액은 `long`을 사용하고 소수 금액은 만들지 않는다.
- 선택 사항은 `HasX`와 값 조합 또는 nullable 중 기존 모델과 맞는 방식을 사용한다.
- 계산 근거는 `EvaluationReasonState` 같은 breakdown 상태로 남긴다.
- 게임 밸런스 상수는 실제 조정 필요가 확인되기 전까지 새 설정 계층을 만들지 않는다.

## 완료 조건

- 각 계산식의 입력, 출력 범위, 가중치, 처리 순서가 명시되어 있다.
- 정상값, 경계값, 잘못된 입력 사례가 각각 최소 하나 있다.
- 같은 입력과 시드의 결과가 항상 같다.
- JSON 저장 후 다시 불러와도 원본 상태와 결과 근거가 보존된다.
- 결과를 두 번 적용해도 금액과 상태가 중복 변경되지 않는다.

## 다음 확정 대상

첫 대상은 경기 평가식이다. 현재 `MatchEvaluator`와 테스트에 이미 구현된 공식을 표로 옮기고, 미정 항목만 결정한다. 그다음 프로모 평가, 쇼 평가와 재정, 장기 변화 순으로 진행한다.
